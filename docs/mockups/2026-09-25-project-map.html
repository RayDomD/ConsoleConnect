Q13 · Project knowledge

Where does the brief learn about the project: docs, decisions, and brand?

Q12 settled that console-connect brief tells every tool what it needs. It draws on three layers. The team and task state come live from the host. Project knowledge belongs in the repository, since the spec says "Git owns code and document history." The question is how the brief knows which files matter and when to read them. Every worker's worktree already contains these files, so the tools can open them directly.

Team and work Live from host

Changes minute to minute, so it's never written to a file.

  • Members, roles, assigning rule (Q11)
  • Open tasks and states, auto settings (Q9)
  • What needs a person's click (Q4)

Project and brand From the repo

Changes through commits, reviewed like code.

  • Spec, PRODUCT.md, DESIGN.md (brand)
  • docs/adr, docs/plans, docs/decisions, docs/mockups
  • Where things live and when to read them

This task From the task

Only for workers, added to their brief.

  • The brief (Q6) and linked decisions
  • The files the map says to read for this kind of task
AAuto-detect known files

The brief scans for known names (PRODUCT.md, DESIGN.md, docs/adr…) and lists what it finds. Nothing to write.

Brand identity rides along

DESIGN.md and PRODUCT.md are in the map with "when to read" rules, so a worker on a UI task is told to follow them. Nothing about the brand is copied into Console Connect.

Branch-correct

Workers read the map from their worktree, so they see the docs as of their branch. The orchestrator reads it from main.

Starts itself

With no map, the brief falls back to A and offers "Draft a project map", which writes a starter docs/README.md for the team to review and commit.
